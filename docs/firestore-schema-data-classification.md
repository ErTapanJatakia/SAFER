# SAFER Firestore schema and data-classification baseline

**Status:** proposed schema v1; documentation only  
**Security posture:** production Firestore client access remains deny-all  
**Compatibility:** current application models are browser-local; this proposal is not a migration contract

This specification records the current SAFER data shape and establishes a safer tenant-storage boundary. It does not authorize production reads/writes or imply that every existing field is suitable for cloud storage. Existing localStorage records must remain local unless a future, separately reviewed, explicit migration is approved.

## 1. Design decisions

1. All operational records are tenant-scoped beneath `/organisations/{orgId}`.
2. Firestore document IDs are opaque IDs generated by the client or a trusted operator; IDs are not authorization.
3. Every tenant record includes immutable `orgId`, `createdAt`, `createdByUid`, `updatedAt`, and `updatedByUid` metadata. Rules must bind UID and timestamps to the authenticated request; clients cannot supply arbitrary provenance.
4. Use ISO 8601 UTC timestamps for Firestore timestamp values. Existing date-only and locale-formatted strings must be normalized in a migration adapter, never silently reinterpreted.
5. Keep documents small and purpose-specific. Avoid unbounded nested arrays, large narratives, attachments, and duplicated personal data.
6. Firestore Rules cannot hide individual fields in a returned document. Confidentiality boundaries require separate documents/collections.
7. Do not store real personal, health, identity, employment, incident, or evidence data in cloud Firestore during this design phase. Use synthetic data only.
8. Production rules remain deny-all until a future rules PR and its positive/negative emulator suite are reviewed.

## 2. Data classification

| Class | Examples in current application | Proposed storage treatment |
|---|---|---|
| Public/demo | Fictional demonstration scenarios, generic checklists, static educational content | Keep bundled/static where practical; no tenant access needed |
| Tenant operational | Synthetic personnel reference, operational role labels, sector assignment, qualification status, incident type/status/priority | May be considered for a narrowly scoped tenant document after schema validation |
| Confidential personal | Full name, display name, call sign, official/personal email, birth date, marital status, addresses, work history, employer contacts | Separate restricted documents; not in broad operational summaries |
| Special-category / highly sensitive | Blood group, health particulars, rare phenotype details, medical first-aid incident narrative | Exclude from initial Firestore phase; separate design, lawful basis, minimisation, retention and stricter access review required |
| Security-sensitive | Incident narratives, witness information, involved people, raw notes, evidence references, security findings, access anomalies | Separate restricted incident/evidence records; no general member read access |
| Governance/audit | Membership changes, approvals, access/security events, export and disclosure events | No client-authored authoritative audit writes; trusted provenance design required |

The application currently combines many of these classes inside a single `PersonnelRecord`. That shape must **not** be copied as one Firestore document.

## 3. Proposed collection and document layout

```text
/users/{uid}
/organisations/{orgId}
/organisations/{orgId}/members/{uid}
/organisations/{orgId}/personnel/{recordId}
/organisations/{orgId}/personnelPrivate/{recordId}
/organisations/{orgId}/incidents/{incidentId}
/organisations/{orgId}/incidentRestricted/{incidentId}
/organisations/{orgId}/evidence/{evidenceId}
/organisations/{orgId}/auditEvents/{eventId}
```

No root-level collection-group access is planned. Do not use a global `personnel`, `incidents`, or `members` collection.

### 3.1 User profile: `/users/{uid}`

Allowed purpose: minimal user preferences only.

Proposed fields:
- `uid`: exact path UID.
- `displayName`: optional user-controlled display label, maximum 100 characters.
- `locale`: allowlisted locale code.
- `themeId`: allowlisted theme identifier.
- `createdAt`, `updatedAt`: Firestore timestamps.

Exclude email, phone, organisation role, membership status, personal data imported from personnel records, and platform-admin flags. Authentication identity remains in Firebase Auth. User can read/update only their own allowlisted preferences; profile values never confer authority.

### 3.2 Organisation: `/organisations/{orgId}`

Proposed minimal fields:
- `orgId`: exact path ID.
- `displayName`: required, maximum 120 characters.
- `status`: operator-managed enum `active | suspended`.
- `schemaVersion`: integer, initially 1.
- `createdAt`, `createdByUid`, `updatedAt`, `updatedByUid`: controlled metadata.

No fictional DPO, address, legal entity, jurisdiction, compliance status, subscription, billing, or security assurance defaults. Do not imply a tenant has legal or regulatory status that has not been verified. Organisation creation and status changes are operator-only/deferred.

### 3.3 Membership: `/organisations/{orgId}/members/{uid}`

Required fields:
- `uid`: exact path UID.
- `orgId`: exact path organisation ID.
- `role`: `owner | admin | manager | viewer`.
- `status`: `active | suspended | revoked`.
- `createdAt`, `createdByUid`, `updatedAt`, `updatedByUid`.

No email-based identity matching, invitation secrets, arbitrary capabilities, custom claims, or client-set timestamps. All membership writes remain denied to application clients. Only the controlled bootstrap/operator process described in the lifecycle policy may seed membership while the trusted provisioning model is unresolved.

### 3.4 Personnel operational summary: `/organisations/{orgId}/personnel/{recordId}`

Initial v1 allowlist proposal:
- `recordId`: exact path ID.
- `orgId`: exact path tenant ID.
- `employeeRef`: tenant-local pseudonymous reference, maximum 64 characters; do not use government ID, badge number, or another externally meaningful identifier.
- `displayLabel`: optional operational label, maximum 80 characters; do not assume it is anonymous if it can identify a person.
- `operationalRoles`: array of at most 10 allowlisted labels, each maximum 60 characters.
- `specialisations`: array of at most 10 allowlisted labels, each maximum 80 characters.
- `assignmentSector`: allowlisted enum; avoid storing precise location in this summary.
- `qualificationSummary`: at most 30 small objects containing `qualificationCode`, `completionDate`, `expiryDate`, and `verificationStatus`; no certificate scans or verification secrets.
- `readinessStatus`: allowlisted enum.
- `requiresHumanReview`: boolean.
- `createdAt`, `createdByUid`, `updatedAt`, `updatedByUid`.

This collection is still confidential personal data when a label or role identifies a person. Manager write access is **disabled**. Proposed initial role access is owner/admin read and create/update only after the rules and field validation pass; manager/viewer access requires a separate decision and test. Deletes are disabled for all roles pending retention/legal-hold policy.

### 3.5 Restricted personnel detail: `/organisations/{orgId}/personnelPrivate/{recordId}`

Potential fields from the existing model include legal/full name, personal contact details, birth date, marital status, blood group, health particulars, structured residence/correspondence addresses, employer names/addresses/contact numbers, detailed work history, administrative notes, and identity-linked documents.

This is a separate high-sensitivity data domain, **not enabled in schema v1**. Do not implement rules or UI access for it in the first tenant-access release. A future design must justify each field, minimise collection, define retention and deletion/legal-hold behaviour, specify purpose and access, and include privacy review. Health particulars and blood-group details require especially strict necessity review and should default to exclusion.

### 3.6 Incident summary: `/organisations/{orgId}/incidents/{incidentId}`

Potential v1 fields:
- `incidentId`, `orgId`.
- `referenceNumber`: tenant-local unique reference, maximum 64 characters.
- `incidentType`: strict allowlisted enum matching the app's supported categories.
- `dateReported`: Firestore timestamp.
- `title`: maximum 160 characters.
- `status`: strict allowlisted workflow enum.
- `priority`: `Routine | Moderate | High Attention`.
- `summary`: maximum 2,000 characters; only after security/privacy review confirms it contains no restricted details.
- `reportedByUid`: authenticated UID, not a free-form name.
- `locationLabel`: optional coarse label, maximum 120 characters; no precise coordinates or access instructions.
- `createdAt`, `createdByUid`, `updatedAt`, `updatedByUid`.

Incident summary content remains confidential and may itself contain sensitive information. For the first access-control release, only owner/admin read/create/update may be considered; manager and viewer reads/writes remain disabled until a separate field/content policy is approved. Deletes are disabled.

### 3.7 Restricted incident details: `/organisations/{orgId}/incidentRestricted/{incidentId}`

Contains any raw notes, factual chronology, people and roles involved, witness information, unverified claims, detailed location, actions taken, follow-up questions, medical details, or information that could identify affected persons. This collection is **not enabled in schema v1**. Do not copy the current `StructuredIncidentDraft` as a single broad-read document.

### 3.8 Evidence metadata: `/organisations/{orgId}/evidence/{evidenceId}`

Potential fields, only after a separate evidence-handling review:
- `evidenceId`, `orgId`, `incidentRef`.
- `evidenceType`: allowlisted enum.
- `description`: maximum 500 characters; no sensitive narrative.
- `referenceCode`: opaque reference, maximum 80 characters.
- `recordedAt`: Firestore timestamp.
- `recordedByUid`: authenticated UID.
- `integrityAlgorithm` and `integrityDigest`: optional validated metadata only, never a substitute for chain-of-custody controls.
- `createdAt`, `createdByUid`, `updatedAt`, `updatedByUid`.

No binary files, download URLs, storage paths, secrets, raw evidence, or attachment bytes. Firebase Storage is out of scope. Evidence metadata remains restricted; manager/viewer access is disabled in v1.

### 3.9 Audit events: `/organisations/{orgId}/auditEvents/{eventId}`

Reserved for future trusted audit architecture. No browser client create/update/delete permissions. Do not claim client-generated events are immutable or authoritative. Do not enable audit reads until confidentiality, retention, and trusted event provenance are defined.

## 4. Role/capability resolution for schema v1

To remove ambiguity in the earlier proposed matrix, adopt the following conservative implementation target for a future rules PR:

| Resource | Owner | Admin | Manager | Viewer |
|---|---|---|---|---|
| Own user preferences | Read/update allowlist | Same | Same | Same |
| Organisation metadata | Read | Read | No access | No access |
| Membership | No client writes; no client reads in v1 | No client writes; no client reads in v1 | No access | No access |
| Personnel operational summary | Read/create/update; no delete | Read/create/update; no delete | No access | No access |
| Restricted personnel detail | No access in v1 | No access in v1 | No access | No access |
| Incident summary | Read/create/update; no delete | Read/create/update; no delete | No access in v1 | No access in v1 |
| Restricted incident detail | No access in v1 | No access in v1 | No access | No access |
| Evidence metadata | Read only in v1 | Read only in v1 | No access | No access |
| Audit events | No client access in v1 | No client access in v1 | No access | No access |
| Organisation/member administration | No client access | No client access | No access | No access |

This is a deliberately narrow starting point. It avoids granting manager writes based on an imprecise field-level policy. Owner/admin document writes must still validate exact fields, authenticated provenance, immutable IDs, tenant consistency, and server timestamps. Any role not explicitly granted access is denied.

**No deletion is enabled for tenant operational records in v1.** Retention, legal hold, correction, archival, and privacy-request requirements must be designed before deletion or destructive updates are considered.

## 5. Field validation and size limits

The future rules and client validators must enforce:
- exact allowed key sets per operation, with no unknown fields;
- strict string/array/object/boolean/timestamp types;
- bounded string lengths and bounded array/object sizes as specified above;
- enumerations rather than arbitrary role, status, priority, or category strings;
- immutable `orgId`, record ID, creator UID and creation timestamp;
- `createdByUid` and `updatedByUid` equal authenticated UID for client-originated writes;
- `createdAt` and `updatedAt` equal `request.time` where the Rules API permits exact timestamp comparison;
- referenced incident/personnel IDs belong to the same organisation and are readable under the caller's permission;
- no client-supplied `role`, `status`, or membership data in operational record writes;
- no arbitrary map nesting or unbounded arrays.

Firestore Rules have expression and document-size limits. Complex schema validation may require splitting documents rather than accumulating deeply nested validation expressions. Rules are not a substitute for full application-level semantic validation.

## 6. Manager permissions — explicit decision

Managers are **read/write disabled for all Firestore tenant collections in schema v1**. The earlier matrix's generic “manager operational contributor” description is superseded by this more conservative decision. Manager UI controls must not be interpreted as authority. A later change may propose a specific capability, such as updating a limited incident workflow field, only after:
1. the exact fields and transitions are specified;
2. restricted content is separated;
3. immutable fields and transition rules are defined;
4. positive and negative emulator tests prove the boundaries;
5. the policy and UI behaviour are reviewed together.

## 7. Migration compatibility and data exclusions

The current TypeScript `PersonnelRecord` includes direct identifiers, personal contact data, birth/marital data, blood group, health particulars, residential addresses, employer contact details, work history, certifications, notes, and readiness fields. Do not map it directly to a Firestore document.

The current `IncidentReport` and `StructuredIncidentDraft` include reporter/location/narrative data, involved people, witnesses, evidence references, raw notes, unverified claims, and follow-up actions. Do not map them directly to a broad-access Firestore document.

No real localStorage data is migrated. A future opt-in migration must:
- show a field-by-field preview and classification;
- exclude high-sensitivity fields by default;
- require the user to select the target organisation and confirm;
- validate schema version and all fields;
- report skipped/rejected records without silently dropping data;
- preserve local originals and existing exports/redaction features;
- never run in the background.

## 8. Required emulator test matrix for the future rules PR

The future rules implementation must test at least:

- unauthenticated user denied every path;
- authenticated user without membership denied tenant records;
- active owner/admin permitted only the explicitly allowed v1 operations;
- manager and viewer denied all tenant operational reads/writes in v1;
- suspended/revoked/missing membership denied;
- user A cannot read/write user B profile or another tenant;
- spoofed `orgId`, record IDs, creator UID, updater UID, timestamps, and cross-tenant references denied;
- unknown fields, oversized strings/arrays, invalid enum values, wrong types and malformed nested objects denied;
- immutable fields cannot be changed;
- deletes denied for all operational records;
- all client audit-event operations denied;
- restricted collections denied to every client;
- list/query requests cannot expose another tenant or broaden access;
- legitimate owner/admin create/update with exact valid schema succeeds;
- owner/admin cannot mutate membership or grant roles through operational documents.

Tests must run against the exact candidate rules in the Firestore Emulator in CI. The suite must contain both positive and negative cases; a suite of only expected failures is insufficient.

## 9. Release gate and explicit non-goals

This specification does not:
- modify `firestore.rules`, `firebase.json`, or client data access;
- create Firestore documents or seed membership;
- enable tenant reads or writes in production;
- enable restricted personnel/incident collections;
- migrate localStorage data or upload any records;
- add Firebase Storage, Cloud Functions, Cloud Run, Admin SDK credentials, Analytics, SMS, phone authentication, or billing;
- claim authoritative client-side audit logging.

The production rules published in Firebase Console must remain deny-all until a separate implementation PR passes positive and negative emulator tests and a security review. If the current project cannot safely support a required operation within the approved zero-cost architecture, defer that operation.
